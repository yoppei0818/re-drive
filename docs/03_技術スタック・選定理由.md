# 03｜技術スタック・選定理由

## 採用方針

| 領域 | 採用候補 | 役割 |
| --- | --- | --- |
| Mobile | React Native + Expo + TypeScript | iOS / Androidアプリ |
| Backend | FastAPI + Python + Pydantic | ルート生成、評価、外部API統合 |
| Auth / DB | Supabase Auth + PostgreSQL | 認証、設定、履歴、保存 |
| Map | Google Maps Platform | Routes、Places、Geocoding |
| AI | OpenAI API または Amazon Bedrock | 説明文、アドバイス生成 |
| Navigation | Google Maps URLs | 外部ナビへの経路引き渡し |

## React Native + Expoを第一候補とする理由

- TypeScriptやWeb開発の経験を活用しやすい
- 外部REST APIとの通信を実装しやすい
- iOSとAndroidを同じコードベースで展開しやすい
- MVPの中心機能は現在地、API通信、地図表示、外部アプリ連携であり、高度なiOS固有機能を必要としない

## SwiftUIとの比較

SwiftUIはMapKit、Core Location、iOS権限、バックグラウンド機能との統合で優位です。iOS専用に絞り、ネイティブ開発の習得を優先する場合は有力な選択肢になります。

現時点ではMVPの完成速度と将来のAndroid展開を重視し、React Native + Expoを採用候補とします。Phase 0の技術検証で地図表示や外部アプリ連携に重大な制約が見つかった場合は再評価します。

## 地図の役割分担

- アプリ内表示：React Native対応のApple MapsまたはGoogle Mapsライブラリ
- ルート計算：Google Routes API
- 場所検索：Google Places API
- 座標・住所変換：Google Geocoding API
- 実ナビ：Google Mapsアプリまたはブラウザ版

## AIの採用順

1. MVPコア：自前の決定論的スコアリングのみ
2. 次段階：AIで評価理由と注意点を生成
3. 将来：運転履歴を使ったパーソナライズ

AIは地理的事実や交通状況を生成せず、バックエンドから渡された特徴量のみを説明します。また、決定論的に算出した難易度を上書きしません。

## セキュリティ上の前提

- Google、OpenAI、Bedrockの秘密鍵はバックエンドで保持する
- モバイルアプリからLLM APIを直接呼ばない
- SupabaseでRow Level Securityを有効化する
- サービスロール鍵をクライアントに配置しない
- ログへ座標や個人情報を不用意に残さない
